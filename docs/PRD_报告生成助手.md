## 1. 产品概述

### 1.1 产品定位

授信报告生成助手是一款面向银行客户经理的 AI 辅助工具。其核心能力是：客户经理上传企业原始材料和报告模板，系统自动生成一份可直接用于审批决策的专业授信调查报告。

报告质量标准：可以直接提交给审批人员，而非仅作参考草稿。

### 1.2 目标用户

- **主要用户**：银行对公客户经理、小微/普惠金融客户经理
- **次要用户**：授信审批人员（报告的接收方，对报告质量有判断标准）

### 1.3 核心价值

| 痛点 | 现状 | 产品解决方案 |
|------|------|-------------|
| 报告撰写耗时长 | 一份授信报告需要 2-4 小时手工撰写 | 上传材料后自动生成，大幅缩短时间 |
| 数据填写易出错 | 手工填写财务数据，转录错误影响决策 | Python 精确计算，数据直接从原始材料提取 |
| 分析质量参差不齐 | 不同客户经理分析深度差异大 | 标准化分析框架，保证分析维度完整 |
| 模板示例污染 | 模板示例内容被遗留在报告中 | 全文档审查机制，自动检测并改写残留内容 |

### 1.4 核心设计原则

**原则一：零幻觉**
金融领域绝对不允许捏造数据。系统只输出可从材料中追溯的事实，以及有证据链支撑的分析推断。

**原则二：读懂 → 分析 → 撰写（Agent 思维，非机械填空）**
系统不是简单地把材料内容粘贴进模板，而是理解材料含义，结合行业背景做分析，再按报告规范撰写。

**原则三：三层信息框架**

| 层级 | 数据来源 | 处理方式 | 质量要求 |
|------|---------|---------|---------|
| 第一层：材料事实（零容错）| 上传的企业材料（财务报表、营业执照、合同等）| 直接提取，Python 精确计算财务比率，不经 LLM 推算 | 与原材料 100% 一致，任何偏差视为严重错误 |
| 第二层：行业上下文（标注来源）| Web 搜索（行业报告、政策文件、新闻资讯）| 检索后标注来源，不直接作为事实陈述 | 来源可追溯，区分"据报道"与"已证实"|
| 第三层：分析推断（证据链支撑）| 基于第一、二层信息的综合判断 | LLM 生成，但必须有明确的事实支撑 | 逻辑自洽，结论与数据相符，不出现无依据的判断 |

## 2. 功能清单

### 2.1 P0 功能（MVP，当前已实现）

#### 材料接入

- **模板上传**：支持 .docx 格式的银行自定义报告模板
- **企业材料上传**：支持 PDF、Word、Excel，支持多文件同时上传
- **OCR 解析**：对扫描版 PDF 进行文字识别，支持表格结构还原
- **Excel 解析**：支持财务报表 Excel 的结构化数据提取（多 sheet、合并单元格等）

#### 智能解析与知识构建

- **知识库自动构建（material_kb）**：从材料中提取结构化企业信息，包括：
  - 公司基本信息（名称、注册地、注册资本、成立时间）
  - 主营业务描述
  - 股东结构与实际控制人
  - 上下游关系（主要客户、主要供应商）
  - 经营资质（许可证、认证等）

- **财务事实库（truth_financial_data）**：
  - 直接从 Excel/PDF 财务报表提取原始数据
  - Python 精确计算所有财务比率（资产负债率、流动比率、净利润率等）
  - 计算结果作为"数据锚点"注入后续所有 LLM 调用

- **企业画像锚点**：综合以上信息生成结构化企业画像 JSON，在每次 LLM 调用时注入 prompt，防止模板示例内容污染生成结果

#### 模板处理

系统支持两类模板，处理策略不同：

| 模板类型 | 特征 | 处理策略 |
|---------|------|---------|
| 普惠模板 | 包含示例填写内容，有真实的示例企业名和数据 | 识别示例内容并替换，重点防止示例企业信息残留 |
| 对公模板 | 仅有字段标题和框架，无示例内容 | 直接填写，风险相对较低 |

#### 字段识别与填写（5 类槽位）

模板扫描阶段将所有待填写位置分为 5 类，分别处理：

| 槽位类型 | 示例 | 处理方式 |
|---------|------|---------|
| XX 字段 | XXX公司名称XXX、XX贷款金额XX | 批量提取，映射到知识库字段 |
| 复选框 | □是 □否、■长期 □短期 | 判断逻辑推断后选择 |
| 示例段落 | 包含示例企业信息的叙述性段落 | LLM 基于 KB 改写 |
| 嵌套表格 | 财务数据表格（多行多列）| 结构化填充 + 精确数据注入 |
| 标签字段 | [行业类别]、[风险等级] | 基于分类规则判断填写 |

#### 财务分析生成

- Python 计算所有财务指标后，LLM 基于精确数值撰写分析段落
- 分析维度包括：偿债能力、营运能力、盈利能力、成长能力
- 分析段落需与计算数值严格匹配，不得出现与数据相悖的表述

#### Phase C 全文档审查（兜底机制）

- 生成完成后，将报告与原始模板做指纹对比
- 检测所有与模板高度相似（未被改写）的段落
- 对检测到的残留内容进行补充改写
- 确保没有任何模板示例内容遗漏在最终报告中

#### 质量校验（QC）与 Blocker 机制

QC 规则引擎检测以下问题类型：

| 规则类型 | 检测内容 | 严重级别 |
|---------|---------|---------|
| 假名检测 | 报告中出现模板示例企业名（如"XX科技有限公司"）| error（阻断输出）|
| 模板区间数字 | 出现明显的示例数字区间（如"5000-10000万元"）| error（阻断输出）|
| 指导语残留 | 模板中的填写说明未被清除（如"请根据实际情况填写"）| error（阻断输出）|
| 行业错配 | 报告内容与企业实际行业明显不符 | warning（提示）|
| 占位符残留 | XX、【】、[]等占位符未被替换 | error（阻断输出）|

**Blocker 机制**：所有 severity=error 的 QC 问题会阻断报告输出，要求修复后才能下载

### 2.2 P1 功能（近期规划）

- **模板库管理**：
  - 通用库：平台预置行业模板（按行业/银行类型分类）
  - 客户私有库：银行自行上传，仅对该行客户经理可见

- **报告在线预览 + 人工修订标注**：
  - 浏览器内预览生成报告
  - 支持对特定段落标注"需修改"，添加批注
  - 修订记录可导出

- **Web 搜索增强**：
  - 自动检索企业所在行业的政策背景
  - 自动检索行业市场规模、增速等数据
  - 检索结果标注来源，作为第二层信息注入报告

- **多模型切换**：支持 DeepSeek、MiniMax、GLM 等模型，平台可配置

### 2.3 P2 功能（远期规划）

- **审批流集成**：预留接口，支持报告生成后提交人工审核流程
- **历史报告管理**：已生成报告的存档与检索
- **相似企业报告复用**：基于行业/规模相似度，推荐历史报告作为参考
- **报告质量评分**：审批人员对报告质量打分，持续优化模型

## 3. 技术架构

### 3.1 当前架构（本地部署版）

**整体流程**：用户 → Gradio UI → agent.py（主控）→ FormFillAgent（form_filler.py）

**处理阶段**：

| 阶段 | 名称 | 说明 |
|------|------|------|
| Phase 0 | 模板指纹采集 | 采集模板原始内容的特征向量，用于后续 Phase C 对比 |
| Phase 1 | 材料解析 + KB 构建 + Truth 财务库 | OCR/Excel 解析 → material_kb + truth_financial_data |
| Phase 2 | 模板扫描（5 类槽位识别）| 遍历模板所有段落和表格，分类标记待填写位置 |
| Phase 3 | XX 字段批量提取填充 | 从 KB 中查找对应值，直接替换 |
| Phase 4 | 复选框判断 + 标签字段填写 | 基于规则或 LLM 判断，选择对应选项 |
| Phase 5 | 示例段落改写（KB 优先 + LLM 改写）| 优先用 KB 数据直接替换，再由 LLM 润色改写 |
| Phase 6 | 表格填充 + 财务分析生成 | 财务数据精确注入 + LLM 生成分析段落 |
| Phase C | 全文档模板残留审查 + 补充改写 | 指纹对比检测 → 未改写段落 → 补充改写 |
| Phase 7 | 占位符清理 + 格式修复 | 清除所有残留占位符，修复格式问题 |
| Phase 8 | 质量校验 + 输出 | QC 规则引擎 → Blocker 判断 → 输出 filled_report.docx |

### 3.2 目标架构（平台适配版）

适配银行 AI 中台的多 Agent 平台（如 Dify、FastGPT、自研 Agent 平台等）。

**架构分层**：

| 层级 | 组件 | 说明 |
|------|------|------|
| 入口层 | 平台对话窗口 | 用户通过自然语言交互 |
| 编排层 | 主 Agent（报告编排）| 理解意图，调度工具，聚合结果 |
| 工具层 | 工具 1：材料解析 | OCR + Excel 解析 |
| 工具层 | 工具 2：财务提取 | 财务数据精确提取和计算 |
| 工具层 | 工具 3：报告生成 | 模板填充 + LLM 改写 |
| 工具层 | 工具 4：质量校验 | QC 规则引擎 |
| 工具层 | 工具 5：Web 搜索 | 行业信息检索 |
| 知识库层 | 模板库（通用 + 私有）| 存储和检索报告模板 |
| 知识库层 | 行业知识库 | 行业特征、政策法规 |
| 数据层 | 企业画像 JSON、财务锚点数据、生成配置 | Agent 间共享的结构化数据 |

#### 平台配置参数

| 配置项 | 推荐值 | 说明 |
|-------|-------|------|
| 模型 | DeepSeek-chat 或同等 | 长文本理解能力强，成本合理 |
| 温度（Temperature）| 0.3 | 降低创造性，提高事实准确性 |
| 携带上下文轮数 | 10-20 | 视材料量调整，材料多时需更长 |
| 最大回复长度 | 128000 tokens | 完整报告内容较长 |
| 知识库 | 模板库（通用 + 私有）| 支持检索匹配对应模板 |

## 4. 质量控制体系

质量控制是本产品的核心竞争力，分为以下几层：

### 4.1 数据层质量控制

| 机制 | 说明 |
|------|------|
| 财务数据 Python 精确计算 | 所有财务比率由代码计算，不依赖 LLM 估算，保证精度 |
| 数据锚点注入 | 计算结果作为"数字锚点"注入每次 LLM 调用的 prompt，覆盖模板示例值 |
| KB 优先改写 | 主营业务、上下游关系、实控人等从材料直接提取，不经过 LLM 创作 |

### 4.2 生成层质量控制

| 机制 | 说明 |
|------|------|
| 企业画像锚点注入 | 每次 LLM 调用前注入完整企业画像 JSON，确保所有生成内容与企业实际情况一致 |
| 模板指纹机制 | Phase 0 采集模板指纹，Phase C 基于指纹检测所有未改写内容 |
| 三层信息框架约束 | prompt 中明确要求 LLM 区分三类信息来源，不得混用 |

### 4.3 输出层质量控制（QC 规则引擎）

**QC 检查流程**：

1. 生成完成的报告进入 QC 环节
2. 规则逐条扫描
3. 判断是否存在 severity=error 的问题
   - **是** → 输出被阻断，返回问题清单，修复后重新触发生成
   - **否** → 生成报告文件供下载，附带 warning 级别问题提示

## 6. 关键设计决策说明

### 6.1 为什么用 Python 计算财务比率而不是 LLM？

LLM 在数学计算上存在固有误差，且在处理多年期财务数据对比时容易混淆数字。财务数据是授信报告的核心内容，一旦错误会直接影响审批决策。因此，所有财务比率必须由 Python 代码从原始 Excel 数据精确计算，计算结果以"锚点"形式注入 LLM prompt，LLM 只负责基于正确数字撰写分析文字。

### 6.2 为什么需要 Phase C 全文档兜底？

前面各 Phase 按槽位类型分别处理，但模板中可能存在无法被正则或规则识别的示例内容（例如嵌入在正常叙述中的示例企业名）。Phase C 通过与原始模板指纹对比，从"结果侧"兜底检测所有遗漏，是整个流程的最终安全保障。

### 6.3 为什么需要 Blocker 机制？

银行授信报告直接影响审批决策，假名残留、模板数字等问题如果出现在提交给审批人员的报告中，会影响银行专业形象，更重要的是可能导致错误决策。Blocker 机制确保这类高风险问题必须修复才能输出，而不是以警告形式被忽略。

## 8. 开放问题与风险

| 问题 | 风险级别 | 处理方案 |
|------|---------|---------|
| 扫描版 PDF 的 OCR 准确率 | 中 | 接入专业 OCR 服务，对关键字段做人工复核提示 |
| 非标准模板格式兼容性 | 中 | 建立模板测试集，上线前做兼容性验证 |
| 超长材料导致的上下文溢出 | 高 | 知识库检索替代全文注入，KB 存储关键信息 |
| LLM 幻觉导致的数据错误 | 高 | 三层信息框架 + 数据锚点 + QC 规则兜底 |
| 模板版本更新的兼容问题 | 低 | 模板版本管理，变更时重新生成指纹 |
