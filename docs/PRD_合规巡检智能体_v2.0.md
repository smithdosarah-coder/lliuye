## 0. 背景：为什么要重写 v1.0

### 0.1 v1.0 的致命问题

v1.0 是「单文件合规查询工具」：上传一份政策文件 + 一份业务记录 → LLM 逐条对比 → 合规清单 + 整改计划。

**演示中客户一眼看穿**：
- 银行的合规是**矩阵问题**，不是一对一对比：几十份监管政策 × 上万条业务记录，你一次只能处理一对一，我要的是矩阵扫描。
- 我每次做专项合规检查，至少要涵盖 3-5 份政策 + 上万条台账，你这个「上传一份政策 + 一份记录」的设定，演示时我看一眼就知道是玩具。
- 合规检查的真正价值是**定位到具体业务单号**：哪条放款违反哪条条款，能立刻调阅原始合同——你这个"上传一份业务记录"模式根本做不到。

**产品定位错误的本质**：v1.0 是把「LLM 对比」做成了产品主干，但合规的本质不是对比两份文档，而是用**政策规则集**去扫描**全量业务事件流**。v1.0 缺少规则集、事件集的抽象，直接让 LLM 做原文对比，既不精确也不可扩展。

### 0.2 v2.0 的根本转变

| 维度 | v1.0（错） | v2.0（对） |
|------|-----------|-----------|
| 输入单位 | 一份政策 + 一份业务记录 | 知识库（N 份政策 + 本行制度 + N 份业务数据） |
| 核心动作 | 两份文档 LLM 对比 | 条款 × 事件 矩阵比对 |
| 输出形态 | 合规率 + 清单 | 分级违规榜单（严重/一般/观察） + 单违规详情 + 整改建议 |
| 单位精度 | 条款级 | 条款 × 业务单号级（精确到放款编号） |
| 用户场景 | 单次合规核查 | 专项巡检（互联网贷款合规 / 反洗钱合规 / 消保合规...） |
| 产品隐喻 | 合规对账本 | 合规雷达屏 |

**一句话重定位**：v2.0 是**知识库驱动的批量合规扫描雷达**，客户上传「监管政策库 + 内部制度 + 业务数据」三类知识库，Agent 把政策拆成规则集、业务拆成事件集，做矩阵比对，吐出违规榜单。

### 0.3 与 Agent1 / Agent4 的共性

三个 Agent 共用一套「知识库扫描范式」：

```
KnowledgeBase（客户上传的锚）
      ↓
RuleExtractor（规则/事件抽取器，LLM 驱动）
      ↓
ScanTargets（扫描目标集合）
      ↓
Matcher（规则 × 事件 矩阵匹配）
      ↓
HitList（命中清单 → 分级榜单）
```

**共享接口**：`SearchProvider` / `KnowledgeBase` / `RuleExtractor` / `Matcher` — **定义和实现规范见《共享架构_知识库扫描范式_v1.0.md》**，本 PRD 不重复定义。

**一致的前端雷达范式**：分级榜单（左） + 违规详情切换（中） + 整改建议卡片（右） + 顶部统计条。

### 1.3 目标用户

| 用户 | 场景 | 价值 |
|------|------|------|
| 银行合规部 | 专项合规巡检（互联网贷款、反洗钱、消保） | 从「人工抽查」到「矩阵全扫」 |
| 内审部 | 内部审计前置合规自查 | 提前发现违规，避免被审出 |
| 风险管理部 | 新政策落地前的差距分析 | 用新政策规则集扫存量业务，量化合规缺口 |
| 总行科技部 | 为合规部门交付 AI 工具 | 基础 Agent 可插拔替换政策库 |

### 1.4 核心价值主张

- **从「一对一」到「N × M 矩阵」**：N 条规则 × M 条业务 = N·M 个比对单元，全部批量跑完。
- **精确到业务单号**：违规不仅指向条款号，还直接指向放款编号/合同编号，合规人员可一键调阅原始记录。
- **分级可操作**：严重/一般/观察三级，每级有明确整改期限和责任部门。
- **政策即配置**：客户上传新政策 PDF → 自动抽成规则集 → 用新规则扫全量业务，无需手工维护规则。

## 2. Demo 目标

### 2.1 演示目标

| 维度 | 目标 |
|------|------|
| 演示时长 | 单场景 4-6 分钟，双场景完整演示 10-12 分钟 |
| 演示对象 | 银行合规部负责人、内审部、总行风险管理、总行科技部 |
| 证明什么 | AI 可从政策文件自动抽规则集，从业务数据自动抽事件集，完成矩阵比对并精确定位违规业务单号 |
| 核心展示 | 规则抽取进度 + 事件抽取进度 + 矩阵扫描进度 + 违规榜单 + 条款 × 业务双向追溯 |
| 预置场景 | 2 个：互联网贷款合规 + 反洗钱合规 |
| 导出能力 | 分级榜单 Excel + 整改报告 Word |
| 体验标准 | 50 条规则 × 100 条业务 矩阵扫完 ≤ 3 分钟，过程可见 |

### 2.2 反「伪雷达」体验硬指标

1. **上传必须是知识库（三类文件多份上传）**，不是「一份政策 + 一份业务」。
2. **扫描过程必须展示规则抽取和事件抽取两个阶段**，客户能看到「政策被拆成 50 条规则」「业务被拆成 100 个事件」。
3. **输出必须精确到业务单号**：点击违规条目能直接看到「放款编号 XXX 违反第 X 条」。

## 3. 演示场景设计

### 3.1 场景 1：「互联网贷款合规专项巡检」（主场景）

**业务背景**：2020 年银保监会发布《商业银行互联网贷款管理暂行办法》，2022 年《商业银行互联网贷款管理办法》更新。某股份制银行合规部对本行 2025Q4 互联网贷款业务进行专项合规自查。

**知识库上传**：
- **监管政策**：
  - `商业银行互联网贷款管理办法.pdf`（3800 字，含 7 章 58 条）
  - `关于进一步规范商业银行互联网贷款业务的通知.pdf`（1800 字）
- **内部制度**：
  - `本行互联网贷款业务操作规程.docx`（5200 字）
- **业务数据**：
  - `2025Q4 互联网贷款放款台账.xlsx`（100 条放款记录）
  - `2025Q4 联合贷款合作记录.xlsx`（30 条合作数据）
  - `风控模型上线记录.xlsx`（15 条模型变更）

**扫描流程（Demo 动画）**：

1. KB 加载完成 → 展示 "2 份政策 · 1 份内部制度 · 3 份业务数据"。
2. **阶段 1：规则抽取**（进度条 `已抽 0/2 份政策`）
   - 政策 1 → 抽出 38 条 `RuleItem`
   - 政策 2 → 抽出 12 条 `RuleItem`
   - 内部制度 → 抽出 18 条 `InternalRuleItem`
   - 共 **68 条规则**
3. **阶段 2：事件抽取**（进度条 `已处理 0/3 份业务数据`）
   - 放款台账 → 100 条 `LoanEvent`
   - 联合贷款合作 → 30 条 `CooperationEvent`
   - 风控模型上线 → 15 条 `ModelEvent`
   - 共 **145 条事件**
4. **阶段 3：矩阵比对**（进度条 `已比对 0 / 68×145 = 9860`）
   - 硬规则先走（业务字段匹配）→ 过滤掉明显不相关的组合
   - LLM 辅助判定剩余 ~300 个模糊单元
5. **输出违规榜单**：
   - 🔴 严重违规：5 条
   - 🟡 一般缺陷：8 条
   - 🟢 观察项：12 条

**预埋违规（预设）**：

| # | 违规类型 | 触发条款 | 涉及业务单号 | 严重度 |
|---|---------|---------|------------|--------|
| 1 | 个人消费贷款期限超限 | 政策1-第6条（期限≤1年） | LN20251108 / LN20251211 | 严重 |
| 2 | 风控模型未独立验证 | 政策1-第18条 | ML20251015 | 严重 |
| 3 | 联合贷款出资比例不足 | 政策2-第3条（≥30%） | COOP202510007 / COOP202511003 | 严重 |
| 4 | 互联网贷款额度超限 | 政策1-第8条（单户≤20万） | LN20251021 | 严重 |
| 5 | 未在 5 个工作日内上报 | 本行制度-第12条 | ML20251122 | 严重 |
| 6-13 | 贷后管理频次不足、披露要素缺失等 8 条 | 多条款 | 多业务号 | 一般 |
| 14-25 | 流程优化类 12 条 | 多条款 | 多业务号 | 观察 |

**单违规详情样例**：

```
【违规 #3】联合贷款出资比例不足（严重）
─────────────────────────────────────────
触发条款：
  《关于进一步规范商业银行互联网贷款业务的通知》第 3 条
  "商业银行与合作机构共同出资发放贷款，单笔贷款中商业银行
   出资比例不得低于 30%。"

涉及业务单号（2 条）：
  · COOP202510007（合作方：XX 小贷 / 本行出资 15%）
  · COOP202511003（合作方：YY 消金 / 本行出资 22%）

证据：
  · COOP202510007 原始记录：放款 500 万，本行 75 万，合作方 425 万（15%）
  · COOP202511003 原始记录：放款 200 万，本行 44 万，合作方 156 万（22%）

整改建议（LLM 生成 + 模板混合）：
  [立即] 暂停上述 2 笔合作方新增放款
  [立即] 重新议定出资比例至 ≥ 30%，补充合同附件
  [7 天内] 对 2025 年所有联合贷款合同做出资比例专项复核
责任部门：零售信贷部 / 法律合规部
整改期限：15 个工作日内完成
```

#### 5.2.4 `matrix_matcher.py` — 规则 × 事件 矩阵比对（核心）

```python
class MatrixMatcher(Matcher):
    """规则集 × 事件集 矩阵比对

    性能优化：两阶段过滤
    1. 硬规则阶段（fast path）：
       - 通过 category 和 event_type 过滤不可能相关的组合
       - 通过 threshold 做结构化比较（如期限>12 月、出资比例<30%）
       - 90% 以上的单元格在此阶段被过滤（要么明确违规要么明确合规）
    2. LLM 阶段（slow path）：
       - 对硬规则无法判定的模糊单元格，调用 LLM 判定
       - 复用 compliance_checker.check_compliance 的单元判定能力
    """

    def match(self, rule_set: RuleSet, event_set: EventSet) -> ComplianceMatrix:
        """返回完整矩阵的命中结果"""

    def _hard_rule_filter(self, rule: RuleItem, event: EventItem) -> Optional[MatrixCell]: ...
    def _llm_judge(self, rule: RuleItem, event: EventItem) -> MatrixCell: ...
```

**数据模型**：

```python
class MatrixCell(BaseModel):
    rule_id: str
    event_id: str
    status: str                  # violate / comply / not_applicable
    severity: str                # critical / major / minor / none
    evidence: str                # 证据（LLM 给出或硬规则给出）
    match_reason: str            # 判定理由

class ComplianceMatrix(BaseModel):
    cells: list[MatrixCell]      # 仅保留 violate 和 partial 的单元格
    rule_count: int
    event_count: int
    duration_seconds: float

class ViolationRecord(BaseModel):
    """聚合后的违规记录（一条违规可能关联多个业务单号）"""
    violation_id: str            # VIO-001
    rule: RuleItem               # 触发的规则
    events: list[EventItem]      # 涉及的所有业务事件
    severity: str                # critical / major / minor
    evidence_chain: list[EvidenceItem]
    recommendation: str          # 整改建议（LLM 生成）
    responsible_depts: list[str]
    deadline: str

class ComplianceLedger(BaseModel):
    severe: list[ViolationRecord]
    normal: list[ViolationRecord]
    observation: list[ViolationRecord]
    stats: dict
```

## 7. LLM 调用规划

### 7.1 LLM 调用点

| 调用点 | 模块 | 输入 | 输出 | Prompt |
|--------|------|------|------|--------|
| 政策分段抽取 | rule_set_builder | 政策章节文本 | list[RuleItem] | `SYSTEM_POLICY_PARSE`（保留） |
| 内部制度抽取 | rule_set_builder | 制度章节文本 | list[RuleItem] | `SYSTEM_INTERNAL_RULE_EXTRACT`（新增） |
| 业务文本事件抽取 | event_extractor | 业务自由文本 | list[EventItem] | `SYSTEM_EVENT_EXTRACT`（新增） |
| 矩阵单元格判定 | matrix_matcher | RuleItem + EventItem | MatrixCell | `SYSTEM_MATRIX_JUDGE`（新增） |
| 批量整改建议 | agent 聚合阶段 | list[ViolationRecord] | 批量 recommendation | `SYSTEM_RECOMMENDATION_BATCH`（新增） |

### 7.2 成本控制

- **场景 1 的 LLM 调用预算**：
  - 规则抽取：按章分 10 段 ≈ 10 次
  - 事件抽取：Excel 直解析（无 LLM）+ 少量文本抽取 ≈ 2 次
  - 矩阵判定：硬规则过滤后约 300 个模糊单元 → 批量（10 个/批）≈ 30 次
  - 整改建议：25 条违规 → 批量（5 条/批）≈ 5 次
  - **合计：约 47 次 LLM 调用**
- **预置场景缓存**：和 Agent4 相同策略。

### 7.3 新增 Prompt 样例（`SYSTEM_MATRIX_JUDGE`）

```
你是一名银行合规专家。请判断某条业务事件是否违反某条监管/内部规则。

输入：
- 规则（rule_id / article_no / condition / source_text）
- 事件（event_id / event_type / fields / raw_record）

输出 JSON：
{
  "status": "violate" | "comply" | "not_applicable",
  "severity": "critical" | "major" | "minor" | "none",
  "evidence": "涉及事件字段的原文摘录",
  "match_reason": "一句话说明为何违反/合规/不适用"
}

判断原则：
- 必须基于输入事件的客观字段判定，不得臆测
- "not_applicable" 用于：规则的适用对象与事件类型不匹配（如针对"个人消费贷款"的条款不适用于"公司贷款"事件）
- 证据必须直接来自事件字段，不得杜撰
```

| 三类 KB 必须分槽位上传 | 少于 3 类无法开始扫描 |
| 两阶段抽取可见 | 前端必须展示「N 条规则」「M 条事件」过程数字 |
| 业务单号必带 | 每条违规必须指向具体单号，不是"某些业务" |

## 10. 非功能需求

### 10.1 性能

| 项 | 目标 |
|----|------|
| 68 × 145 矩阵扫描 P95 | ≤ 3 分钟 |
| 榜单视角切换 | ≤ 500ms |
| 矩阵规模上限 | 支持 200 条规则 × 1000 条事件（LLM 调用 ≤ 100 次） |

### 10.2 可扩展性

- 规则集可在运行时追加 / 编辑（生产场景合规人员手工补充）
- EventExtractor 的字段映射支持自定义（不同银行业务字段不同）
- MatrixMatcher 的硬规则阶段可注册自定义函数（如时效类 T+N 校验）

### 10.3 可解释性

- 每条违规都能展示：为什么硬规则命中 / 为什么 LLM 判为违规（输出判定理由）
- 条款原文与业务原文双向对照展示
- 合规人员可在 UI 上手动标记"误报"，Demo 阶段记录用于 Prompt 优化

### 10.4 合规与安全

- 业务数据不出本机
- 整改报告可本地导出 Word，避免通过网络传输敏感业务数据
- LLM 调用可选用本地模型（Qwen / DeepSeek 本地部署）

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 矩阵规模爆炸（200×1000=20万单元） | 扫描超时 | 硬规则阶段必须过滤 ≥ 90%；剩余 LLM 批量（10/批） + 并发 |
| LLM 对条款理解偏差 | 漏报/误报 | 建立条款语义测试集（每条条款 3 正例 + 3 反例）回归验证 |
| 业务字段名称不统一 | EventExtractor 失败 | Demo 阶段用 field_dict.json 明确映射；生产需要字段映射配置向导 |
| 政策 PDF 扫描件 OCR 质量差 | 规则抽取失败 | 预处理阶段加 OCR 置信度检查，低置信度给出警告 |
| 客户质疑"你的规则抽得全吗" | 信任度下降 | 抽取结果可查看 + 可编辑（补漏机制），展示"共抽出 68 条 · 已去重 7 条" |
| 整改建议太通用 | 价值感低 | LLM 生成时强制要求结合具体业务单号和金额，模板托底 |

## 13. 附录：与 Agent1 / Agent4 的一致性清单

| 维度 | Agent1 获客 | Agent4 贷中 | Agent5 合规 |
|------|------------|-------------|-------------|
| 输入 | 客户池 + 渠道库 + 行业政策 | 客户池 + 规则库 + 内部制度 | 政策库 + 内部制度 + 业务数据 |
| 抽取阶段 | 政策 → 行业趋势 | 内部制度 → 规则 | 政策 → 规则集 + 业务 → 事件集 |
| 匹配方式 | 企业 × 渠道 评分 | 企业 × 双路规则 交叉 | 规则 × 事件 矩阵 |
| 输出榜单 | 推荐渠道 Top 榜 | 红黄绿客户榜 | 严重/一般/观察违规榜 |
| 详情切换 | 企业详情 + 渠道适配矩阵 | 客户详情 + 证据链 | 违规详情 + 条款原文 + 业务原记录 |
| 建议卡片 | 营销建议 | 处置建议 | 整改建议 |
| 共享接口 | `KnowledgeBase` / `Matcher` / `SearchProvider` | `KnowledgeBase` / `Matcher` / `RuleExtractor` / `SearchProvider` | `KnowledgeBase` / `Matcher` / `RuleExtractor` |
| 视觉范式 | 分级榜单 + 详情 + 建议 | 分级榜单 + 详情 + 建议 | 分级榜单 + 详情 + 建议 |
| 导出 | PDF 推荐报告 | Excel 榜单 + PDF 处置单 | Excel 榜单 + Word 整改报告 + PDF 整改单 |

**结论**：Agent5 在雷达范式下是「把合规问题建模为规则-事件矩阵」的特化版本，与 Agent4「把贷中风险建模为外部-内部双路交叉」形成对偶。二者共用 `KnowledgeBase` / `RuleExtractor` / `Matcher` 接口和前端雷达范式，客户看到的是统一产品，内部是针对不同领域对象的特化实现。
