1. **MAJOR：Gate-0 与“可直接开工”互相冲突。**  
   §8 把三个 BLOCKER 全放在 P-1 之前；§14 又说 P-1/P0 无需拍板、可直接开工。必须拆成：

   - Gate-0A：P-1/P0 开工门，只确认发布门确定契约；
   - Gate-0B：P1/P2/P3 各自授权门。

2. **MAJOR：发布失败策略仍存在双实现口径。**  
   §4.1 写“拒绝导出，或返回水印草稿”，没有说明由哪个 policy_version、哪项配置决定。应固定状态映射，禁止开发者现场二选一。

3. **MAJOR：P0 错称“无新架构”，工期仍有自欺。**  
   §4.3 的 immutable ledger 流水线、§4.1 的导出契约重构都属于结构性变更；将四项连测试和生产发布压进 2–3 天，缺少接口调用方盘点、兼容迁移和灰度验证预算。

4. **MAJOR：P0 发布门依赖尚未闭合。**  
   §4.1 要“重跑 blocker/verifier”，但 §5.1 的 claim verifier 又受 IP gate 约束。P0 必须明确只调用哪些仓库内现有检查器；否则可能把尚未获授权的 verifier 变成 P0 隐性依赖。

5. **MAJOR：P1 收窄略有矫枉过正。**  
   平账五态、行业分位数、趋势拆 RFC 是正确的；但“财务一致性最小检查”不能与发布门拆开。否则 P1 可以形成证据完备、流程闭环、数字却不勾稽的“可信假象”。应保留原创的最小会计恒等式/单位/期间/口径一致性检查，不必移植 dd-engine 平账闸。

6. **MINOR：Gate-0 缺少可签署产物。**  
   当前只有决策事项，没有每闸的 owner、批准记录位置、有效期、失败状态和复核日期，尚不能机械判断 PASS/FAIL。
