## 0. 一页纸摘要

**判定：骨相好，命门断，护栏缺。** 架构方向在 2026-04 就对了（确定性判断层、规则外置 JSON、SSE 证据事件、run_id 审计、RBAC）——正是后来 dd-engine、律所线、日照方案反复验证的同一套哲学。但**可信性三支柱在实现层全部被旁路**，且升级本身有三道开工前必须闭合的闸门。

三支柱断裂（主会话亲验，R1 复核属实）：
1. **验证不拦产出**：QC blocker 只打日志；QC FAIL 照落 docx 给下载链；**导出接口允许客户端传 `qc={"passed":true}` 覆盖服务端判定**（api.py:1393-1394 亲验）
2. **缺数造词**：`_DEMO_SAFE_FALLBACK` 42 键把缺失字段填成「本企业/成立多年/符合本行准入」——为演示不穿帮伪造内容
3. **证据不落盘**：EvidenceItem 协议定义了却不产出持久台账，审贷员点不开任何数字看出处

**升级主线 = 把「可信判断」从口号做成机器保证**：单一权威产物（ArtifactVersion）+ 纯函数发布门（evaluate_release，fail-closed）+ 字段级证据台账（与已有 decision_ledger 主外键关联，不造第二真相源）+ 缺数四态 provenance 契约。

**分期（R1 重排）**：`P-1 基线闸`（安全/卫生/基线清零）→ `P0 诚信线`（服务端重算发布门 + 去造词 + 去判断层预埋）→ `P1 最短可信闭环`（冻结快照—字段证据—单一发布门，报告线单切片）→ 里程碑重估后再排 P2（MCP，需 IP gate）/ P3（交互）/ P4（harness）与 P1 的扩展件（平账闸/双轨阈值/趋势各自立 RFC）。

**只对外承诺 P-1 + P0 + P1 单条报告闭环的工期（约 2-2.5 周）；完整范围先做 1 周 spike 出依赖图再逐里程碑重估——不给未实测的压缩承诺（R1-10）。**

**与日照 C021 关系**：升级版 = C021 受控 POC 的参照实现基座（四 Agent 框架直接映射）；验收纪律与 C021 §6 成熟度分级表同源。

## 2. 升级原则（第一性）

1. **可信判断四不可让渡**：验证不过不产出；缺数不装懂；数字可回链；同一事实快照下判断可复现。演示效果问题用「演示数据质量」解决，不用「伪造输出」解决
2. **权威只在服务端**：任何质量/发布判定由服务端对不可变产物重新求值，**客户端不得提供权威 QC/发布状态**（R1-1）
3. **哑铃架构**：进料智能 — 判断确定（零 LLM）— 出料智能（逐句校验）。本次把两端闸门装上
4. **demo 与判断层物理隔离**：预埋数据只能做输入 fixture 走真规则引擎，永不覆盖判断输出；mock/live 状态单一事实源（R1-6）
5. **单一真相源**：证据/决策/发布状态各有唯一权威存储，跨存储只存引用不复制正文（R1-8）
6. **改在正确的层**：前端发现数值错误回数据层修，不在展示层打补丁
7. **保留视觉定稿**：乾策 Studio 视觉语言是历史多轮 PM 验收的定稿；本次改动按 Q-047 最新校准区分**逻辑层（可直接施工）vs 审美层（逐项先问 PM）**（R1-13）

## 5. P1 · 最短可信闭环（R1-9 收窄 · 报告线单切片）

> R1-9：v1 的 P1 把缺失四态+平账闸+编译门+表覆盖+verifier+台账+发布状态机+双轨+趋势全塞一期，范围失控。**v2 的 P1 只做最短闭环三件，其余各自立 RFC。**

### 5.1 单一权威产物 + 纯函数发布门（R1-7 核心）

- 定义 `ArtifactVersion`（冻结正文 + facts_snapshot + policy_version + run_id + facts_fingerprint）
- 纯函数 `evaluate_release(artifact, facts_snapshot, policy_version) → verdict`：**固定检查次序 + severity 映射**；任何校验器异常/超时/版本缺失 → `blocked`（fail-closed）
- 发布状态机（`阻断→水印草稿→可发布→已发布`）**只消费该唯一 verdict**——收敛现有 quality_scorer(75 分制) 与 quality_blocker(五维) 的口径分裂，不新增第三套
- **P1 验收基线与增强件分离（R3-1 闭合 · 唯一口径）**：`evaluate_release` 的 **P1 验收基线 = 仓库内现有检查器（quality_blocker/numeric_validator/output_validator）+ §5.3 最小财务一致性四项**——**不含 claim verifier**，P1 完成判定只按此基线，不存在第二种质量标准。claim verifier（六契约）是 **IP gate 过后才接入的增强检查器**，接入时 `policy_version` 升版并补对应负例——它不阻塞 P1，也不参与 P1 验收；财务一致性维接真 anchor（修 section_generator.py:987 恒 None，属基线内）

### 5.2 字段级证据台账（与 decision_ledger 关联，R1-8）

- **不造第二真相源**：字段证据台账存事实+来源（raw/normalized/unit/period/source_span/confidence/human_action）；已有 `shared/decision_ledger` 只引用冻结的 `evidence_snapshot_id / artifact_version / policy_version`
- 发布事务**原子固化**这些引用；禁止复制可独立漂移的证据正文
- 生产链真消费：material_anchor 提取时逐字段落台账；每个数字绑 ledger 键；`GET /api/report/evidence/{run_id}` 暴露
- 空壳 evidence_pipeline.py：接真或删除

### 5.3 缺数四态 + 最小财务一致性检查（R2-5：这一维不能拆出发布门）

- financial_analyzer / truth_fill 输入层引入 `present / true_zero / missing_unknown / not_applicable`——「缺数不算绿」；缺失不按 0
- **最小会计一致性检查（原创，非 dd-engine 平账闸移植，留在 P1 发布门内）**：会计恒等式（资产=负债+权益）/ 单位一致 / 期间对齐 / 口径一致 四项确定性校验，作为 evaluate_release 的一个检查器。**理由（R2-5）**：若把财务勾稽全拆去 RFC-A，P1 会造出「证据完备、流程闭环、数字却不勾稽的可信假象」——比现状更危险。完整 47 条勾稽/平账五态状态机才拆 RFC-A（那是 dd-engine 移植 + IP 件），最小四项恒等式是原创、不涉 IP、本轮必做

### 5.4 P1 明确不做（各立独立 RFC，授权+版本化后再排）

- **完整平账闸五态状态机 + 47 条勾稽**（dd-engine 移植）→ RFC-A（含勾稽规则来源与 IP，见 §11③）；**注意：§5.3 的最小四项恒等式不在此列，本轮必做**
- **A/B 双轨阈值的 B 轨（行业分位数）**→ RFC-B：**无权威基准来源/样本口径/行业分类版本前，只输出「基准不可用」，不得形成准入结论**（R1-9 强调防伪精确）
- **多期趋势规则（T0/T1/T2）**→ RFC-C
- Agent6→Agent3 结构化 handoff → 随 §5.1 台账落地捎带，但契约单独冻结

**工程量**：先 1 周 spike 出依赖图+接口契约+基准耗时（R1-10），再估。**只承诺「报告线单条 DP001 级 case 走通冻结快照—字段证据—单一发布门」**，不承诺全 6 Agent。

**验收（R1-11，机器判定）**：给测试文件 + 命令 + 固定输入哈希 + 逐字段 oracle + 阈值 + CI 阻断条件；golden case 由双人业务复核签署，覆盖缺表/错期/单位错/合并口径/负数/真零/OCR 错/矛盾材料——**不能仅靠回归一致性（会固化旧错）**。
