## 二、报告生成助手

### 2.1 是什么

读取银行信贷模板（.docx），结合客户材料（财务报表、企业资料等），用 LLM 自动填写生成完整的授信调查报告。

### 2.2 关键文件

位置：`D:\claude code\credit_report_agent_work\`

| 文件 | 用途 |
|------|------|
| app.py | Gradio 前端入口（当前版本 v7.23）|
| agent.py | 核心 Agent 调度逻辑 |
| form_filler.py | 表单填写引擎（6000+ 行，核心文件）|
| llm.py | LLM 调用封装（支持 DeepSeek / MiniMax / Kimi）|
| tools.py | 工具函数（OCR、文件解析等）|
| prompts.py | 提示词 |
| truth_fill.py | 结构化数据预填充（财务数据精确计算）|
| quality_check.py | QC 质量校验规则引擎 |
| config.py | 模型配置（含 DeepSeek / MiniMax）|
| test_run.py | CLI 测试脚本（绕过 Gradio 直接跑）|
| outputs/ | 生成的报告文件 |
| docs/ | PRD 文档 |

### 2.3 处理流水线（form_filler.py）

| 阶段 | 名称 | 说明 |
|------|------|------|
| Phase 0 | 模板指纹采集 | 采集模板所有段落的文本指纹，用于后续 Phase C 对比 |
| Phase 1 | 材料解析 + KB 构建 | OCR/Excel 解析 → material_kb + truth_financial_data |
| Phase 2 | 模板扫描 | 遍历模板，识别 5 类槽位（XX字段/复选框/示例段落/表格/标签）|
| Phase 3 | XX 字段填充 | 从 KB 匹配并替换 |
| Phase 4 | 复选框 + 标签 | 规则或 LLM 判断选择 |
| Phase 5 | 示例段落改写 | KB 优先 + LLM 改写 |
| Phase 6 | 表格填充 + 财务分析 | 精确数据注入 + LLM 生成分析段落 |
| Phase C | 全文档模板残留审查 | 指纹对比检测未改写段落，**迭代式**（最多3轮，收敛即停）|
| Phase 7 | 占位符清理 + 格式修复 | 清除残留占位符 |
| Phase 8 | 质量校验 | QC 规则引擎，severity=error 阻断输出 |

### 2.4 核心机制

**企业画像锚点**：每次 LLM 调用前注入企业画像 JSON（公司名/主营/行业/注册资本/实控人/营收），防止 LLM 使用模板示例企业信息。

**数据锚点**：所有财务比率由 Python 精确计算（truth_fill.py），作为"锚点"注入 LLM prompt，LLM 只负责写分析文字，不做计算。

**Phase C 迭代审查**（v7.23 新增）：
- 扫描 → 改写 → 再扫描 → 再改写，循环最多 3 轮
- 收敛检测：残留数不减少则停止
- 拆成 `_phase_c_scan_residuals()` 和 `_phase_c_rewrite_residuals()` 两个独立方法

**QC Blocker**：假名残留、模板数字、指导语残留等 error 级问题会阻断报告输出。

### 2.5 当前质量状态

| 模型 | 问题数 | 主要残留问题 |
|------|-------|------------|
| DeepSeek | 5-8 类 | 65-70%/240员工/芯片相关模板内容、10,10万元格式 |
| MiniMax (m2.5) | 4 类 | 表现最好，但 65-70%/240员工 仍残留 |

**根本原因**：LLM 在改写时仍然从模板复制部分内容，而不是基于材料重写。Phase C 迭代审查是最新的解决方案，还未用最新代码测试。

### 2.6 已知 Bug / 待修复

- **Gradio UI 中文乱码**：app.py 中的中文注释和 UI 标签存在 mojibake（不影响功能）
- **Phase C 迭代效果未验证**：v7.23 刚完成改动，需要实际跑一次报告验证

## 三、平台导入计划

### 3.1 目标

将报告生成助手导入公司自研 AI 中台，作为"客户经理个人助手"生态的第一个 Agent。

### 3.2 AI 中台平台能力（已确认）

| 能力 | 详情 |
|------|------|
| Multi-Agent 编排 | 主 Agent 可配置子 Agent 作为"工具"调用 |
| 模型 | za.zp.glm-5 |
| 参数 | 温度 0.85、上下文轮数 20、最大回复长度 128000 |
| 工具 | 可添加其他 Agent 作为工具（Agent 类型）|
| 知识库 | 支持文档型知识库（RAG 检索）|
| 变量 | 支持自定义变量，prompt 中用 $变量 引用 |
| 子 Agent | 支持层级编排 |
| 调试 | 右侧调试面板，实时对话测试 |

### 3.3 导入方案（推荐思路 A：整体封装）

将现有 Python 服务用 FastAPI 包一层 REST API，在平台上注册为自定义工具（HTTP 调用）。

**要做的事**：
1. 写 FastAPI 包装层，暴露 `POST /generate` 接口
2. 接收模板 + 材料文件，返回报告文件 + 企业画像 JSON + 财务锚点
3. 在平台注册为工具
4. 模板库接入平台的知识库能力

**暂不做**：拆成多个独立 Agent/工具（当前阶段增加复杂度无收益）。

### 3.4 待确认

用户尚未提供自研平台的具体对接规范（API 接入方式、文件传输、模型调用走平台还是自带）。需要拿到平台的技术文档才能出详细方案。
